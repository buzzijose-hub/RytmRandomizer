# Pi appliance source and authority evidence

Scope: changes to the shared Cockpit appliance, its native-value projection,
runtime packaging or touch acceptance. See the
[learned workflow](../skills/learned/pi-appliance-source-evidence/SKILL.md).

- Bind builds, previews and release verification to the actual integrated source.
  A different editable install or stale wheelhouse must not supply the claimed
  source. Verify retained source/web/assets before activating a rollback.
- Keep simulation authority sealed at session composition. Saved-KIT decoding,
  native value precision and software previews grant no unsaved-state, SEND or
  restore authority. Existing Device/Strategy and ArmedApply boundaries remain
  canonical.
- Measure and inspect the actual production touch layout. Complete modal
  header/footer actions must remain visible; scrollable content cannot hide the
  refusal or exact-action controls in the acceptance screenshot.
- Preserve source/checkpoint distinctions in receipts. Record physical Pi,
  ARM64 and live-hardware gaps explicitly; append run outcomes without erasing
  failed attempts. Write baseline audits before future implementation begins.

Current evidence and continuation instructions live in the
[run report](../../docs/PI_APPLIANCE_RUN_REPORT.md) and
[replay playbook](../../docs/PI_APPLIANCE_REPLAY_PLAYBOOK.md).
